# Business Rules (BR log)

Product/business rules decided during the MVP build that aren't obvious from the
code. Short, running list. (Distinct from the frozen domain corpus in `docs/`,
which is the long-term North Star.)

| ID | Rule | Since | Rationale / notes |
|---|---|---|---|
| BR-001 | **Email identifies a person globally.** One account exists per email address; an individual may belong to only one organization for now. | Story 1.1 | Cleaner than `(email, org)` for enterprise SaaS + future SSO. If we later support agencies/consultants across orgs, introduce a **membership** model — the email→account identity stays. |
| BR-002 | **Organization names are not unique.** Two companies may share a display name; identity is the organization **id**, never the name. | Story 1.1 | Display names are poor identifiers; never block signup on a name collision. |
| BR-003 | **The first user of an organization is its admin.** | Story 1.1 | Signup creates the org + its first `admin` user atomically. |
| BR-004 | **A campaign is always created in `draft`, owned by the creator's organization.** Ownership is set from the verified token and never reassigned. | Story 2.1 | Campaigns are born editable; calibration is frozen only at activation (INV-003). Ownership = tenant id from the token, never the request body (INV-000/INV-001). See `docs/domain-invariants.md`. |
| BR-005 | **A candidate is one identity record per `(organization, email)`, reused across campaigns.** Adding an already-known email to another campaign reuses the existing `Candidate` and creates a new evaluation. | Story 3.1 | Identity (PII) is separate from evaluation (INV-006). Same person across two orgs = two records (each org owns its PII copy). |
| BR-006 | **Candidates can only be added to an `active` campaign, once each.** | Story 3.1 | You calibrate in draft, activate (freeze), then invite. One evaluation per candidate per campaign (INV-007). Résumé upload is an optional object-storage pointer, not the file. |
| BR-007 | **Re-inviting a candidate replaces the previous invitation.** Issuing a new invitation revokes any still-active one for that evaluation, so only the most recent link works. | Story 4.1 | Cleanest security semantics — one live link per evaluation; old links (e.g. forwarded/leaked) stop working. Invitations expire (default 14 days) and are the candidate's only credential (INV-009). |
| BR-008 | **Consent is an append-only versioned fact; granting is idempotent per version.** Re-granting the same active version returns the existing grant (no duplicate). Consent text is governed by a version (`mvp-2026-01`); changing the wording means a **new version** (and, later, re-consent) — never mutating what a past grant meant. | Story 4.2 | Provable later exactly what a candidate agreed to and when. Withdrawal (future) sets `withdrawn_at`; it never deletes or rewrites the grant (INV-010). |
| BR-009 | **A campaign has one Structured Work Sample, editable only while draft, and every competency must be covered by ≥1 task to activate.** Each task maps to ≥1 real campaign competency and carries an evidence intent; the sample derives from the campaign and never redefines what "good" means. | Story 4.3 | The evidence instrument. Save (draft) allows partial progress but every task must be well-formed; full coverage is enforced at activation (INV-011). Task types are text-first for the MVP; scoring/AI live elsewhere. Task definitions are frozen at activation so responses stay interpretable (INV-003). |
| BR-010 | **Candidate work is mutable draft state until final submission; every task requires a non-empty response to submit.** Draft responses autosave and upsert (one per task); they are not Evidence. Drafts may be incomplete, but final submission (Story 4.5) requires every task answered. | Story 4.4 | `WorkSampleResponse` = working state; Evidence is the immutable submitted snapshot (Story 4.5), created atomically and consent-gated — never `status="submitted"`. Every task exists to elicit required evidence, so all must be answered before submission. |
| BR-011 | **Submission requires valid access, active consent, an active/frozen work sample, and one meaningful response for every required task; it is atomic and irreversible.** On success the evaluation is `submitted`, immutable Evidence exists, and the candidate can no longer edit or re-submit (no reopening in MVP). | Story 4.5 | The authoritative transition (INV-012). Any failed check commits nothing (no Evidence, no submitted state, no audit). Idempotent for double-click/retry. Reopening, if ever needed, is a deliberate future capability — not a silent flag flip. |
| BR-013 | **Evaluation execution requires submitted Evidence and active consent; retries are idempotent and reruns are explicit.** A recruiter (admin/recruiter/hiring_manager) triggers an evaluation; it runs only on a `submitted` CandidateEvaluation with active consent (re-checked immediately before persistence — AI processing is a distinct processing action from submission). `evaluate` is idempotent (a repeat, or a repeated `Idempotency-Key`, returns the existing run — never a second one); `rerun` is the explicit action that creates a new immutable run. A provider/validation failure creates no Evaluation and no `evaluation.generated` audit. | Story 5.2 | The safe pipeline must execute end-to-end and produce a durable, reproducible record *before* a real model is introduced (INV-014). No automatic evaluation on submission yet — recruiter-triggered keeps the boundary observable and avoids surprise cost/behavior. Deterministic mock only. |
| BR-012 | **AI output is a *proposal*, and the platform (not the model) owns confidence.** The AI evaluates only submitted evidence, cites it, and returns a recommendation proposal + platform-computed confidence. Confidence means "how reliable is this evaluation given the available evidence" — a `[0,1]` reliability signal, **not** a probability of on-the-job success — and is independent of the recommendation direction. If confidence is below the governed honesty floor, the exposed proposal becomes `ESCALATE`. | Story 5.1 | Evidence-based hiring intelligence, not a scorebot (INV-013). Escalation is a valid, expected outcome (deferring to a human), distinct from a system failure. A high confidence never means "good candidate" — e.g. `DO_NOT_PROCEED` + HIGH confidence is valid. No real model call yet; a deterministic mock proves the pipeline. See `docs/ai-boundary.md`. |
