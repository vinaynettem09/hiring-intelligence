# Domain Invariants (INV log)

These are **promises the product makes** — not implementation details. They outlive
any given function, framework, or refactor. A code review's first question for any
change touching the domain is: *does this preserve every invariant below?* A change
that breaks one is rejected, however convenient.

They are distilled from the frozen architecture corpus (`arch/`, esp. ARCH-03) into
the handful that the MVP must never violate. Each says what is guaranteed and how the
code guarantees it **today** — so we never mistake an aspiration for an enforced rule.

| ID | Invariant | Enforced by (today) | Since |
|---|---|---|---|
| **INV-000** | **Tenant isolation.** No request ever reads or writes another organization's data. The tenant id comes only from the verified access token (the envelope), never from the request body/query/header. | `AuthMiddleware` → envelope → `require_auth`; every tenant-owned query routes through `TenantScopedRepository`, which applies the tenant filter so a caller cannot forget it. A raw `select(SomeTenantModel)` outside it is a review rejection. | Story 1.3 / 2.1 |
| **INV-001** | **Every Campaign belongs to exactly one Organization.** A campaign cannot exist un-owned or be moved between organizations. | `Campaign.organization_id` is `NOT NULL` (FK → `organizations.id`); set from the token at creation and never reassigned; reads go through `CampaignRepository(TenantScopedRepository)`. | Story 2.1 |
| **INV-002** | **Evidence cannot exist without an Evaluation.** The ownership chain is `Organization → Campaign → Candidate → CandidateEvaluation → Evidence`. Nothing downstream floats independently of the campaign it belongs to. | Structural `NOT NULL` FKs at each level. `CandidateEvaluation` now exists (Story 3.1) with FKs to campaign + candidate; Evidence (Epic 5) will FK to it. | Story 2.1 → 3.1 |
| **INV-006** | **Candidate identity (PII) is separate from evaluation.** A `Candidate` (name, email, résumé pointer) is the PII record; a `CandidateEvaluation` is the AI-visible participation record and holds **no PII**, referencing the candidate by id. The evaluation pipeline consumes evaluations + evidence, never the identity record directly. | Two tables: `candidates` (PII) and `candidate_evaluations` (no PII, FK to candidate). One identity record per `(organization, email)`, reused across campaigns; the AI never reads `candidates`. | Story 3.1 |
| **INV-007** | **A candidate participates in a campaign at most once.** No duplicate participation — exactly one `CandidateEvaluation` per `(campaign, candidate)`. | DB unique constraint `(campaign_id, candidate_id)`; intake checks first and raises `CANDIDATE_ALREADY_IN_CAMPAIGN` (409) (or *skips* the row on bulk import). | Story 3.1 |
| **INV-008** | **Candidates may only be added to an `active` campaign.** Not `draft` (still being calibrated — INV-003) and not `concluded` (closed). This guarantees every candidate is assessed against frozen criteria — no "were these evaluated against the old rubric?" ambiguity. | `CandidateService` (single-add and bulk import) raises `CAMPAIGN_NOT_ACTIVE` (409) unless the campaign is `active`. A permanent product guarantee, not a configurable workflow. | Story 3.1 |
| **INV-009** | **A candidate invitation grants access to exactly one `CandidateEvaluation`, and nothing else.** It is a separate trust boundary from recruiter auth: possession of an opaque, hashed, expiring token — never a JWT, never a guessable id. It can never reach another candidate, evaluation, campaign, organization, tenant, or any recruiter/admin API. | `invitations` stores only the SHA-256 hash of the token (raw token never persisted, never logged, no PII inside); resolve joins strictly from that one token to its own evaluation's context; invalid/expired/revoked fail closed with no existence leak. Re-issue revokes the prior active link. | Story 4.1 |
| **INV-010** | **No processing without active consent** (corpus INV-11, now executable). No work-sample processing → no evidence → no AI evaluation unless the candidate has an active consent grant. Consent is an **append-only, versioned fact** (who/which evaluation/which exact version/when; withdrawal via `withdrawn_at`) — never a mutable boolean. Active consent = a non-withdrawn grant exists. | `consents` table + `ConsentService.has_active_consent(evaluation_id)` — the single authoritative gate downstream stories call; **fails closed**. Consent is only grantable through a valid invitation (token resolves the evaluation server-side); the client never supplies an evaluation/tenant id. | Story 4.2 |
| **INV-011** | **Every campaign competency must have ≥1 work-sample task before activation.** If the campaign claims a competency matters but no task can elicit evidence for it, a later evaluation of that competency would be unsupported — which breaks the evidence-first thesis. So a campaign cannot activate unless its work sample exists, has ≥1 task, and covers every competency. | `WorkSampleService.assert_ready_for_activation` (called by `CampaignService.activate`) raises `CAMPAIGN_INCOMPLETE` (422) with `{missing}` / `{uncovered_competencies}` metadata; every task also maps only to real campaign competencies (`WORK_SAMPLE_INVALID`). | Story 4.3 |
| **INV-012** | **Only explicit candidate submission promotes mutable responses into immutable Evidence, and Evidence is the *only* candidate-authored input the AI may evaluate.** Evidence is append-only, PII-free candidate-authored fact. Epic 5 AI consumes `Frozen Role Profile + Frozen Work Sample Task + Evidence` — **never** `WorkSampleResponse` (mutable draft), Candidate PII, résumé, invitation/consent metadata, or arbitrary DB context. | `evidence` table is a **snapshot** (copy, not a pointer) created only by `submit`; `EvidenceRepository` exposes no update/delete; unique `(evaluation, task)` backstops duplicate submission; Evidence carries no PII columns. **Now structural (Story 5.1):** `EvaluationInputAssembler` is the *only* builder of AI input and imports neither `Candidate` (PII) nor `WorkSampleResponse` (draft) — a structural test asserts this; the `EvaluationInput` DTO has no identity fields. Because `Evidence.response_text` is free text that *can* contain PII, a `PIIMinimizer` produces a transient AI-safe projection between Evidence and the provider (Evidence is never mutated). See `docs/ai-boundary.md`. | Story 4.5 → 5.1 |
| **INV-013** | **AI proposes; the domain/human decides — and the platform, not the model, owns confidence.** The AI produces a grounded `EvaluationProposal` (`STRONG_PROCEED…ESCALATE`), never an authoritative `HiringDecision`. Every substantive competency claim must cite Evidence actually present in the input. Confidence is a platform-computed evidence-*reliability* signal, not a success probability, and is orthogonal to direction. | No `HiringDecision`/`hire`/`reject` type exists in the intelligence module; the provider output is untrusted and passes schema → grounding → policy validation before becoming a proposal; ungrounded output is rejected (`UNGROUNDED_OUTPUT`); `ConfidenceCalculator` is platform-owned; a governed **honesty floor** forces `ESCALATE` when confidence is too low, so the provider cannot overrule uncertainty. `ESCALATE` (a valid proposal) is distinct from an `EvaluationFailure` (a system condition). | Story 5.1 |
| **INV-014** | **A persisted Evaluation is an immutable, evidence-grounded AI proposal with durable provenance; reruns create new Evaluation records and never mutate historical ones.** An `Evaluation` is produced only from a validated `EvaluationProposal` (never raw provider output), records its own recommendation/confidence/citations/provenance/input-fingerprint, and is append-only. A rerun is a *new* run; run 1 is never altered. Distinct from `CandidateEvaluation` (the participation lifecycle) and never a `HiringDecision`. | `evaluations` (+ `evaluation_competency_assessments`, `evaluation_citations`) tables; `EvaluationRepository` exposes **no update/delete/save**; `unique(candidate_evaluation_id, run_number)` + `unique(candidate_evaluation_id, idempotency_key)` are DB backstops (proven on real Postgres); flattened provenance columns + `input_fingerprint` (SHA-256 over the PII-safe input) keep a run reconstructable after versions move on. Persistence happens only *after* schema+grounding+policy validation, platform confidence, and honesty-floor enforcement, and only while consent is still active (re-checked immediately before the write). Provider/validation failures persist nothing. | Story 5.2 |
| **INV-003** | **A campaign's configuration is immutable after activation.** Once a campaign is `active`, its `role_profile` (competencies + bar) **and its Structured Work Sample** cannot change. Assessing candidates against shifting criteria — or a shifting instrument — would make results untrustworthy. To change criteria, create a new campaign. | `Campaign.activate()` is the one-way gate into `active`; from then on there is **no code path that edits configuration** — `role_profile` has no update endpoint, and `WorkSampleService.define` rejects any edit unless `status == draft` (`WORK_SAMPLE_LOCKED`). Both become the frozen, trusted input the evaluation pipeline (Epics 4–5) reads, so a candidate's response is always interpretable against the exact task that produced it. | Story 2.2 → 4.3 |
| **INV-004** | **Historical evaluations are append-only.** Scores, evidence, and AI reasoning are never overwritten in place. Corrections and re-runs create *new* records/events; the original stays readable. This is what lets a recruiter trust — and audit — what the system told them at the time. | Planned: evaluation writes are inserts, never updates; audit events are immutable. **Enforcement lands with the evaluation store (Epic 5).** Recorded now so the schema is designed append-only from the start. | Epic 5 |
| **INV-005** | **A campaign never reopens.** The lifecycle only moves forward: `draft → active → concluded`. An `active` or `concluded` campaign can never return to `draft` (or to `active`). Once historical evaluations exist under a campaign, reopening it makes its results impossible to reason about — so instead you create a **successor** campaign. | `Campaign.activate()` raises `CAMPAIGN_NOT_DRAFT` (409) from any non-draft state, so activation is only ever draft→active; there is no `reopen()` and no transition back. (Forward transition `active → concluded` lands with the conclude story.) | Story 2.2 |

## Lifecycle (the campaign state machine)

```
draft ──activate()──▶ active ──conclude()──▶ concluded
  │        (2.2)          │        (later)
  └─ configuration        └─ configuration FROZEN (INV-003); only outcomes accrue
     is editable
        ▲ no path back (INV-005) ─────────────────┘
```

- **draft** — being set up; `role_profile` editable. The only state a campaign is
  *born* into (creation always yields a draft).
- **active** — calibration frozen (INV-003); candidates are assessed against it.
- **concluded** — closed; no new assessments.

Transitions are the model's responsibility (`Campaign.activate()`), so legal-transition
rules live in one place instead of `if status == ...` scattered across services. An
illegal transition raises a domain error (`CAMPAIGN_NOT_DRAFT` 409); an incomplete
campaign raises `CAMPAIGN_INCOMPLETE` (422). `activate()` ships with **Story 2.2**;
`conclude()` (active → concluded) is intentionally **not implemented until its own
story** — we add lifecycle behavior only when a story needs it, never as an empty stub.
